## 6. ⚠️ 核心发现：关系边质量是短板

**结论：内容字段（定义、公式）可直接用；关系字段（parent/child）目前只有约一半可信，需要阶段三复核。**

我做了 4 轮 prompt 迭代对比，同一批数据、同一模型：

| 版本 | 下位边总数 | 清晰错误的上位边 | 说明 |
|---|---|---|---|
| v1（原始措辞） | 2 | 2（填了学科分类名「力学」「运动学」） | 上位最保守，下位几乎为空 |
| v2（明确禁止分类名） | 7 | 3（「能量→功」**反向**、「牛顿第一定律→惯性定律」填了同义词） | **禁令起反作用**，模型开始编造 |
| v3（"是一种"判定法） | 4 | 出现无意义值（动量→「量」），合规率掉到 90% | 最差，已废弃 |
| **v4 / 最终版** | **7** | **4** | 见上表打 ⚠️ 的四条 |

**典型错误类型**

1. **反向边**：`能量.parent = 功`（应为 `功.parent = 能量`）
2. **类比当上下位**：`功率.parent = 能量`（功率是能量转换的**速率**，不是一种能量）
3. **分类名当上位**：`加速度.parent = 运动学`、`万有引力定律.parent = 力`
4. **同义词当上位**：`牛顿第一定律.parent = 惯性定律`
5. **run-to-run 不稳定**：同样 prompt 重跑，关系结果会变——这是 7B 模型的固有限制。

**我的建议（按性价比排序）**

1. **保持现状 + 阶段三人工/联网复核关系边**（推荐）。位定义和公式已经够好，只锁关系，成本最低。
2. 换更大模型（`qwen2.5:14b`）—— 但本机 RTX 4060 只有 8 GB 显存，14B 需部分 CPU 卸载，**约 10% 的上下文会跑到内存，吞吐会腰斩**，不建议为这 100 条付这个代价。
3. 关系边改用**规则 + 清单人工标注**。100 条规模下，人工标 100 条父子关系比调 prompt 更快更准。

> 脚本已内置**自动关系质量体检**，每次运行都会输出：悬空引用、双向闭合率、分类名上位计数。上表结果就是它产出的。

### 7.1 `wikidata_id` / `source_url` 我填了 `null`，没有让模型编

原因不是我偷懒，是**依据你项目自己的纪律**：

> README 第 5 节：「发现来源许可不明时，停止发布流程并生成待审核报告」

离线状态下，7B 模型给的 QID 和 URL 是凭记忆生成的、无法核验的字符串。写进交付文件就是把未经核验的数据伪装成规范来源，直接违反上面这条。

因此本批次的取值：
- `wikidata_id` → `null`（等阶段三联网核验后回填）
- `source_url` → `null`（同上）
- `license_type` → `"UNVERIFIED"`（诚实标记「许可未核验」，而非填入看起来像真的 `CC BY-SA 4.0`）

**如果你希望改成让模型输出猜测值**，不用改代码，加一个参数重跑即可（约 19 秒）：
```powershell

```
